(`buildClusterKey` in `src/lib/person-identity.js`: `${surnameKey}:${sorted memberIds}`). If a

ingested later, or the group's composition changes because an upstream evidence fix changes who

updated or resolved automatically, it just sits there unresolved, orphaned, alongside the new one.

duplicates, and nothing is ever wrongly auto-linked either way), but Task 2 (review-tab) and/or

superseded flags for the same underlying surname cluster over multiple runs, and the review UI/
runbook should account for that (e.g. surface "this cluster_key's candidate set changed since it
was flagged" or periodically reconcile/retire orphaned flags) rather than assuming one flag row per
real ambiguity forever.
